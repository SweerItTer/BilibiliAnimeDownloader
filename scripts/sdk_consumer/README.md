# Independent bili_core consumer

Run the generated commands from the SDK root. The generated `build-info.json` is the authoritative matched-build tuple. In `rlib` mode, `consumer/build-command.txt` compiles `consumer/src/main.rs` against `lib/libbili_core.rlib` and the exact packaged Rust dependency artifacts; it does not rebuild the core. `consumer/source-build-command.txt` is a separate Cargo recipe that rebuilds the included `source/bili_core` using the relocatable `native/` FFmpeg development prefix and `Cargo.lock`.

The rlib verifier actually executes that same generated source command and runs the readonly Core/jobs/shutdown lifecycle; `build-info.json.source_cargo_verification` records it separately from prebuilt-rlib compilation. Native paths expand from the recipient SDK root at command runtime (`$PWD` on POSIX, `%CD%` in Windows CMD), not from a producer checkout. Source-built consumers use their own build artifacts plus the SDK native/runtime libraries; they are not self-contained apps, and their newly built Core dylib is not proof of the prebuilt-dylib SDK.
Both prebuilt modes execute exactly the same SDK-root-relative argv that they serialize into `consumer/build-command.txt`, including separate `-o` and output-path arguments. A matching installed Rust compiler is required to compile these SDK examples, not to run the packaged CLI. Keep source-built and prebuilt proof records separate; a producer-only successful command cannot qualify a different unexecuted recipient command.


Compiler inputs include normal-dependency proc-macro DSOs alongside rlib/rmeta files in `lib/`; Rust metadata can require these even when this consumer does not invoke a macro. Do not remove them as duplicate runtime DLLs. Keep the generated compiler commands and matched artifacts together.

For pkg-config, use the moved SDK's `native/lib/pkgconfig` without producer paths or `--define-variable` overrides. Its prefix, libdir and includedir must all resolve inside that SDK; rewriting only prefix does not relocate absolute libdir/includedir fields.

In `dylib` mode, use the exact recorded `rustc -Vv`, target, profile, flags, and `--extern bili_core` path shown in `build-command.txt`. Linux places the core `.so` and Rust/native runtime libraries in `lib/`, with the consumer in `bin/`, app RUNPATH `$ORIGIN/../lib`, and library RUNPATH `$ORIGIN`. Windows places the core `.dll`, its import `.lib`, and all runtime DLL dependencies beside the consumer in `bin/`; Rust dependency artifacts are in `lib/` and FFmpeg import libraries are in `native/lib/`.
When the Windows SDK includes Microsoft CRT DLLs, it also bundles the pinned source terms and provenance under `licenses/windows-redist/` and the extracted UTF-8 terms in `notices/third_party/`. Review these terms alongside the SDK license notices before redistribution.

The SDK includes the matching relocatable FFmpeg headers and pkg-config metadata under `native/`. Its `.pc` files resolve paths relative to their own location; Linux native libraries are in the SDK `lib/`, while Windows runtime DLLs are in `bin/` and import libraries are in `native/lib/`. Shared FFmpeg libraries are replaceable native dependencies, separate from Rust core linkage. The dylib is a Rust dependency, not a stable ABI or `dlopen` plugin. Rust ABI, layouts, and dependency graph are unstable across builds. Use the same Rust runtime, allocator, and panic strategy; keep handles/futures within the matched process and shut down `Core` before exit. Do not unload or hot-replace the dylib while any Rust value from it is alive. The SDK has no C ABI, `staticlib`, `cdylib`, or hotloading support.
